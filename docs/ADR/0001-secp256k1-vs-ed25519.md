# ADR-0001: secp256k1 (ECDSA) vs Ed25519 for EOA Signatures

## Status
Accepted

## Context
The current `src/wallet.rs` uses `ed25519-dalek` 2.2 for Ed25519 signatures. This is a design decision from the prototype phase. 

Forces at play:
- **Ecosystem compatibility**: Ethereum tooling (MetaMask, Ledger, WalletConnect, Foundry, Hardhat) expects secp256k1 (ECDSA, and future BIP-340 Schnorr). Ed25519 is not supported by any major Ethereum wallet.
- **Cryptographic properties**: Both curves provide ~128-bit security. Ed25519 has faster signing/verification and smaller signatures (64 bytes vs 64 bytes compact ECDSA). secp256k1 enables ECDSA recovery (pubkey from signature) which is useful for on-chain verification.
- **Future-proofing**: Bitcoin Taproot uses BIP-340 Schnorr on secp256k1. Ethereum is moving toward account abstraction with ECDSA/Schnorr. Staying on Ed25519 isolates Strangecoin from this ecosystem.
- **Migration cost**: Rewriting `wallet.rs` is a one-time cost. Keeping Ed25519 requires maintaining dual-curve infrastructure forever.

## Decision
We will migrate the wallet to use `secp256k1` crate (ECDSA) for all EOA (externally owned account) signatures.

Implementation details:
- Crate: `secp256k1 = { version = "0.29", features = ["rand", "serde", "global-context"] }`
- `SigningKey` → `secp256k1::SecretKey` (32 bytes)
- `VerifyingKey` → `secp256k1::PublicKey` (33 bytes compressed)
- Keystore format remains: PBKDF2 + AES-256-GCM + 12-byte nonce (only key material changes)
- Signature format: 64-byte compact (r || s), not DER
- Ed25519 is fully removed from `wallet.rs` (optional return for internal auth deferred to Stage 2)

## Consequences

### Positive
- Full compatibility with MetaMask, Ledger, WalletConnect, and all Ethereum tooling
- Enables future BIP-340 Schnorr signatures without curve change
- ECDSA public key recovery allows on-chain verification without storing pubkeys
- Aligns with ARCHITECT3.md §3.8 and §15 (anti-goal: "Ed25519 для EOA-подписей")

### Negative
- Slightly slower signing/verification than Ed25519 (~2-3x)
- Larger public keys (33 bytes compressed vs 32 bytes)
- Migration requires all existing users to recreate wallets (acceptable at v0.8.6 prototype stage)

### Neutral
- Keystore encryption (PBKDF2 + AES-GCM) unchanged
- Address derivation deferred to P05 (bech32 `sc1...` in Stage 1)

## Alternatives

### Alternative 1: Keep Ed25519 for EOA
- Pros: Faster signatures, smaller pubkeys, existing code works
- Cons: Zero Ethereum tooling compatibility; isolates project from largest crypto ecosystem; violates ARCHITECT3.md explicit anti-goal
- Why not chosen: Strategic incompatibility with long-term goals

### Alternative 2: Support both curves (dual-curve wallet)
- Pros: Backward compatibility during transition
- Cons: Doubles wallet complexity; two code paths to audit; confusion about which key is "primary"; violates "clean core" principle
- Why not chosen: Unnecessary complexity for prototype-stage migration

### Alternative 3: Use k256 (pure Rust) instead of secp256k1 (C bindings)
- Pros: Pure Rust, no C toolchain required
- Cons: Slower; less battle-tested; secp256k1 crate is the de facto standard in Rust Bitcoin/Ethereum ecosystem (rust-bitcoin, ethers-rs, alloy all use it)
- Why not chosen: Ecosystem standard is secp256k1 crate
